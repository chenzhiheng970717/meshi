## ADR-001 平台选网页，不做 iOS 原生首发

**日期** 2026-09-08 · **状态** 已采纳

**背景** 最初设想是 iOS 原生 app。评估了 iOS / 微信小程序 / 网页三条路。

**决定** 先做网页版，iOS 壳等算法稳定后再加。

**理由**
- 推荐引擎是与平台无关的纯函数，输入条件输出排序。真正的不确定性在「排序合不合直觉」，不在 Swift 写得对不对。
- 网页零审核零备案，成本约 $1/月，改完刷新即生效；iOS 每次改动要过 1–2 周审核。
- 微信小程序有两道硬门槛：2023 年 9 月起必须先完成 ICP 备案才能上架（需中国大陆主体 + 境内备案域名）；`wx.getLocation` 需按类目单独审批，个人主体可选类目极窄。定位是本产品的核心功能，接口批不下来等于做不了。

**代价** 放弃了原生定位精度、推送和 App Store 的分发渠道。iOS 上 PWA 的体验也弱于原生。

## ADR-002 店铺数据源选 HotPepper，不选 Yelp / Google

**日期** 2026-09-08 · **状态** 已采纳

**背景** 需要一个能按预算、人数、包间筛选的东京餐厅数据源。

**决定** MVP 用 HotPepper グルメサーチAPI 作为唯一数据源。

**理由**
- 免费。Yelp Fusion 起价 $229/月且日本数据稀薄；Google Places 每千次 $32。
- **原生支持 `budget` / `party_capacity` / `private_room` 参数**——这正是需求里最难自己实现的部分。用 Google 的话，price_level 只有 0–4 四档，人数和包间根本没有。
- 覆盖率实测可接受：东京都各分类件数加总约 11.9 万（去重后约 9–12 万），对比食べログ 东京 13.9 万，约为其 70–85%。

**代价**
- 缺口是结构性的：米其林级高端店、拉面单店、个人咖啡店、不做线上营销的老铺基本不在库里。
- **不返回评分和评论数**，需要另找来源（见 ADR-004）。
- `range` 参数上限 3km，超出需多中心点采样（见 ADR-003）。
- 受 Recruit 条款约束：署名、24h 缓存上限、商用需书面同意。

## ADR-003 超过 3km 的搜索用八方位多中心点采样

**日期** 2026-09-08 · **状态** 已采纳

**背景** HotPepper 的 `range` 最大只有 3000m，而「驾车 30 分钟」的可达半径是 6km。

**决定** 目标半径 > 3km 时，以出发点为圆心、在目标半径上按 8 个方位角取采样点，每点发一次 `range=5` 的请求，结果按 `shop.id` 去重合并。

**理由** 8 次并发请求约 400ms，可接受；而且 API 免费，调用次数不构成成本压力。

**代价** 环形区域覆盖不完整（采样点之间有空隙），中心到采样点之间的中环地带会被重复覆盖。可以接受——推荐场景不需要穷举，只需要足够大的候选池。

## ADR-004 评分接 Google Places，「喜欢」比例并行积累

**日期** 2026-09-09 提出 · 2026-09-10 拍板 · **状态** 已采纳

**背景** 卡片设计里有评分和评论数，但 HotPepper API 不返回这两个字段。

**候选方案**
1. **接 Google Places 补充。** `rating` 和 `userRatingCount` 属于 Enterprise 字段，每月 1000 次免费，超出 $35/千次。单人使用约 $0，但多用户后成本上升快。
2. **只显示自己积累的「喜欢」比例。** 零成本，但冷启动阶段没有数据。
3. **不显示评分，改显示「人气」合成分。** 用图片数、是否有套餐、是否有优惠券合成。零成本，但可信度低。

**决定** 短期用方案 1：搜索结果里对进入前几批的店，服务端按店名 + 经纬度调 Google Places
Text Search / Place Details 取 `rating` / `userRatingCount`，结果随 HotPepper 一起 24h 缓存。
同时方案 2 并行——`likes` 标记落库后计算「喜欢」比例，数据够了就作为主信号，Google 退成兜底。
方案 3 的合成人气分继续作为打分公式里「人气」项的兜底（Google 未命中该店时）。

**理由** 单人使用免费额度足够（每月 1000 次搜索）；Google 的 JP 餐厅覆盖比 HotPepper 全，
正好补上 HotPepper 缺的长尾。自建「喜欢」数据是长期正确方向，但冷启动必须先有个数。

**代价 / 前提（硬约束）**
- **启用当天必须在 Google Cloud Console 设配额上限**（Places「每日请求数」→ 200/天）。
  预算告警只发邮件不阻断计费，配额上限才是熔断器。见 CLAUDE.md。
- Google key 只在 Edge Function 环境变量，绝不进客户端。Places 调用全部服务端 + 缓存。
- 代码里再加一道进程内 / 存储层的当日调用计数硬上限，作为第二道保险。
- 评分是 Google 的，不能落库长期保存（同样按 ≤24h 缓存处理），展示需符合 Google 归属要求。
- 多用户后成本会涨，届时重新评估切方案 2 的时机。

## ADR-005 API Key 走服务端代理，不放客户端

**日期** 2026-09-08 · **状态** 已采纳

**决定** HotPepper API Key 只存在于 Supabase Edge Function 的环境变量里，客户端只调自己的 `/search`。

**理由**
- 客户端的网络请求可以被抓包，Key 泄漏后会被滥用直到被 Recruit 封禁。
- Edge Function 顺带解决另外两件事：缓存（省调用，且符合 24h 条款）和**算法热更新**（改打分权重不用重新部署前端）。
- 成本为零，在 Supabase 免费档内。

**代价** 多一跳网络延迟；本地开发需要跑 Supabase CLI。

## ADR-006 登录只做邮箱 OTP，手机号延后

**日期** 2026-09-08 · **状态** 已采纳

**决定** MVP 只提供邮箱 OTP 与匿名（游客）会话，不做短信登录。

**理由** 日本 SMS 约 ¥12–20/条，是 MVP 阶段唯一会失控的成本项。邮箱 OTP 在 Supabase 免费档内。

**代价** 日本用户对邮箱登录的接受度低于手机号。等有真实用户量再评估。

**附带约束** 核心功能（搜索推荐）**必须允许游客使用**。这既是产品判断，也是未来做 iOS 时 App Store 条款 5.1.1(v) 的硬要求——强制登录会被拒。

## ADR-007 地理编码用 Google Geocoding API

**日期** 2026-09-10 · **状态** 已采纳

**背景** 用户输入的是自由文本地址（「東京都新宿区新宿3-38」甚至门牌号），HotPepper
搜索要的是经纬度。原型阶段用固定演示地址库顶着，正式版需要真的地理编码。

**候选** Google Geocoding / Yahoo! JAPAN ジオコーダ / Nominatim(OSM) / 国土地理院(GSI)。

**决定** 用 Google Geocoding API。

**理由**
- ADR-004 已经上 Google，同一个 key、同一份账单、同一个配额熔断，不多引一套凭据。
- 日本门牌号（番地・号）精度是几家里最好的。
- 属于 Maps Platform 的 Essentials 档：每月 1 万次免费，超出 $5/千次——比 Places
  Enterprise 便宜一个量级，个人使用基本 $0。

**代价 / 前提**
- 同样占 Google 配额，**Cloud Console 里 Geocoding 也要设每日上限**（建议 500/天）。
- 调用在服务端，key 不进客户端。
- 常用地址存 Postgres 时只存解析后的坐标 + 用户原始输入，不缓存 Google 的其他返回字段。
- 定位按钮（`navigator.geolocation`）直接给坐标，不走地理编码，不占配额。
