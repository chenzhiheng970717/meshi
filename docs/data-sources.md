## 对比

| 数据源 | 价格 | 东京覆盖 | 预算/人数字段 | 结论 |
|---|---|---|---|---|
| **HotPepper Gourmet** | 免费 | 约 9–12 万家（食べログ 的 70–85%） | ✅ 原生支持 | **MVP 主数据源** |
| Google Places (New) | Nearby Pro $32/千次，5k 免费/月 | 几乎全覆盖 | ❌ 仅 price_level 0–4 | v1.1 补长尾 + 评分 |

**覆盖实测（东京都）**：HotPepper 官网各分类件数加总约 119,000（和食 25,264 / 居酒屋 23,261 / 咖啡甜点 11,034 / 中华 6,306 / 其他杂项 17,268 等，分类间有重叠）；食べログ 东京 139,211。

**缺口形状**：HotPepper 是营销平台，收录的是愿意做线上获客的店。强在居酒屋、宴会、连锁、可预约、有包间；缺米其林级割烹、拉面单店、个人咖啡店、不做网络营销的老铺、新开业店。

> 「找家能坐 6 个人喝酒的店」用 HotPepper；「想吃那家特定的拉面」用 Google。

## HotPepper グルメサーチAPI

**文档** https://webservice.recruit.co.jp/doc/hotpepper/reference.html
**申请** https://webservice.recruit.co.jp/ （有审核等待，是关键路径上唯一不可控的环节）

### 需求字段映射

| 用户输入 | API 参数 | 备注 |
|---|---|---|
| 地址 | `lat` / `lng` | 需先做地理编码 |
| 距离 | `range` | 只有 5 档：300/500/1000/2000/3000 m，**上限 3km** |
| 人数 | `party_capacity` | 筛出可容纳该人数的店 |
| 口味 | `genre` | 17 个大类码，需先调「ジャンルマスタAPI」获取 |
| 预算 | `budget` | 晚餐预算码，需先调「予算マスタAPI」获取，一次最多 2 个码 |
| 时间 | — | 不支持按时间过滤，需拉回 `open` 字段本地解析 |
| 交通方式 | — | 本地换算为可达半径 |

### 分页与上限

- `count` 每页最多 100（默认 10）
- `start` 结果偏移
- 单次请求 `range` 上限 3000m → 见 [ADR-003](decisions.md#adr-003)

### 已知坑

**`open` 字段是自由文本。** 形如「月～金 17:00～23:30（L.O.23:00）、土日祝 16:00～24:00」。格式不统一，解析器要能优雅降级：解析失败时不过滤，并在 UI 上标注「营业时间请以店家为准」。

> **开工前先做这件事**：抽 100 条真实 `open` 数据人工看格式，再写解析器。别凭想象写正则。

**分类码需要动态拉取。** genre 和 budget 的码表通过对应的 master API 获取，不要硬编码——码表会变。

## 合规要求（Recruit 利用规约）

来源：https://cdn.p.recruit.co.jp/terms/rws-t-1001/index.html

| 要求 | 对代码的影响 |
|---|---|
| **必须显示数据来源署名与 logo** | 页脚固定放「Powered by ホットペッパーグルメ」及官方 logo，不可移除或修改 |
| **缓存不得超过 24 小时** | Edge Function 的缓存 TTL 硬上限 24h；不得把店铺数据写入 Postgres 长期保存 |
| **不得复制进第三方数据库** | 数据库只存用户、标记、常用地址，**不存店铺数据** |
| **不得修改数据或创作衍生作品** | 展示原始字段，不改写店名、地址等 |
| **商用需事先书面同意** | MVP 免费无广告；变现前走官方咨询表单确认 |

## Google Places (New) — v1.1 备用

2025 年 3 月起取消统一的 $200 月度额度，改为按 SKU 分层免费额度：

| 档位 | 每月免费 | 用到的接口 | 超出单价 |
|---|---|---|---|
| Essentials | 10,000 | Geocoding、Autocomplete、地图显示 | $2.83–5 / 千次 |
| Pro | 5,000 | Nearby Search（不含评分） | $32 / 千次 |
| **Enterprise** | **1,000** | **含 `rating` / `priceLevel` / 营业时间** | **$35 / 千次** |

**关键约束**：`rating`、`priceLevel`、`regularOpeningHours` 全是 Enterprise 字段，而打分引擎需要它们 → 实际约束是**每月 1000 次搜索调用**。另外 Nearby Search **每次最多返回 20 条且不支持翻页**，凑 60–80 家候选需 3–4 次调用。

单人使用估算（按每次搜索 4 次调用）：

| 强度 | 月调用量 | 费用 |
|---|---|---|
| 每天 5 次搜索 | 600 | **$0** |
| 每天 10 次 | 1,200 | ≈ $7 |
| 每天 20 次 | 2,400 | ≈ $49 |

### ⚠️ 启用 Google API 的第一件事

**风险不是用量，是 bug。** `useEffect` 依赖数组写错、下拉刷新没防抖，一夜之间能打出几万次调用。5 万次 Enterprise 调用 = **$1,715**，而 Google 必须绑信用卡才能启用 API。

> 在 Google Cloud Console 里设 **配额上限**（Quotas → 每日请求数上限），设成 200/天。
> **预算告警只发邮件、不阻断计费，配额上限才是熔断器。**
> 这一步做在申请 Key 的当天，不要等。

Google 的 Nearby Search 半径上限是 50km，没有 HotPepper 的 3km 限制，所以用 Google 不需要多中心点采样。

## 需要调用哪些 HotPepper API

**一个 API Key 覆盖全部 12 个 API**，注册时不用选服务。注册页只要邮箱，**无人工审核**，验证完即发 Key。

实际用得上的只有三个：

| API | 用途 | 调用频率 |
|---|---|---|
| `グルメサーチAPI` | 主力搜索，所有店铺数据 | 每次用户搜索 |
| `ジャンルマスタAPI` | 口味分类码表（G001 居酒屋…） | 启动时拉一次，缓存 |
| `検索用予算マスタAPI` | 预算区间码表 | 启动时拉一次，缓存 |

后两个**不能跳过**：`genre` 和 `budget` 参数要传码而非文字，且码表会变，硬编码迟早出问题。

用不上的九个：`店名サーチAPI`、`クレジットカードマスタAPI`、五个エリアマスタ系（我们用经纬度搜索，不用区域码）、`特集マスタAPI` / `特集カテゴリマスタAPI`。

### 拿到 Key 后的第一次请求

```bash
curl "https://webservice.recruit.co.jp/hotpepper/gourmet/v1/?key=$HOTPEPPER_API_KEY&lat=35.6912&lng=139.7020&range=3&count=5&format=json" | python3 -m json.tool
```

这一次请求要确认两件事：

1. **候选池大小** —— 以住址为中心 1km、加上预算和人数条件，实际返回多少家店。这会验证或推翻整个数据源选型。
2. **支付方式字段的粒度** —— 原型卡片画了「刷卡 / 现金 / IC 卡 / 扫码」四种，但 `グルメサーチ` 很可能只返回一个粗粒度的 `card` 字段。若是如此，卡片设计需相应收敛。

同时对一遍 `open`（营业时间自由文本）、`photo.pc.l`（店铺照片）、`urls.pc`（店铺页链接）三个字段的真实形态。
