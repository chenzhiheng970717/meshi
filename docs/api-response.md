# グルメサーチAPI 真实响应实测

2026-09-09 实测。请求：`lat=35.6912&lng=139.7020&range=3&count=5`（新宿駅東口，1km）。

**`results_available: 2174`** —— 候选池规模验证通过，HotPepper 单独撑 MVP 没问题。

---

## ⚠️ 五个必须处理的坑

### 1. 默认排序是「おすすめ順」，也就是广告位

实测返回的前 5 条**全是同一栋楼（新宿3-27-10 武蔵野ビル）的连锁居酒屋**：千年の宴、京町恋しぐれ、魚民、楽蔵、かに料理 然。这不是巧合——默认 `order=4`（おすすめ順）本质是掲載プラン排序。

`order` 参数只有 4 个值：`1` 店名かな / `2` ジャンル / `3` 小エリア / `4` おすすめ（默认）。**没有按距离排序**。

**后果**：`count=100` 只拉一页，拿到的是 2174 家里最靠广告的 100 家，本地打分再准也是在一个有偏样本上排序。

**对策**（Edge Function 必须实现）：
1. 先用 `range` + `genre` + `budget` + `party_capacity` 尽量收窄，让 `results_available` 降下来
2. 读 `results_available`，若 > 100 则翻页：`start=1, 101, 201...`，`count=100`
3. 设上限 300–500 条后停止，避免无谓请求
4. 拉完再本地硬过滤 + 打分

### 2. 最大图片只有 238px 宽

```
photo.pc.l  → 238px   photo.pc.m → 168px   photo.pc.s → 58px
logo_image  → 69px
```

**没有大图。** 卡片缩略图（132px）够用，但**详情页做不了大图 hero**。当前原型抽屉里的 150px 高照片区需要重新设计——要么缩小，要么接受模糊，要么改成拼贴。

### 3. `card` 字段只有两个值

```json
"card": "利用可"        // 或 "利用不可"
```

原型卡片上画的「刷卡 / 现金 / IC 卡 / 扫码」四种支付方式**拿不到**。API 只告诉你能不能刷卡。IC 卡和扫码支付没有对应字段。

**对策**：收敛成一个「可刷卡」标记。

### 4. `non_smoking` 是多态字符串，不是布尔

实测出现的值：`"全面禁煙"` / `"一部禁煙"` / `"禁煙席なし"` / `"未確認"`（2026-09 复测新增第 4 个值）

原型按布尔处理，需要改成多态显示。解析器把 `未確認` 及未知值归为 `unknown`。

### 5. 设施类字段是「あり/なし ：自由文本」格式

```json
"private_room": "あり ：2名様14室、4名様23室、6名様14室、8名様8室、10～70名様6室"
"private_room": "なし ：詳細はお問い合わせください。"
"horigotatsu":  "あり ：掘りごたつ席のご希望はお気軽にご相談下さい。"
```

`private_room` / `horigotatsu` / `tatami` / `parking` / `barrier_free` / `charter` / `free_drink` / `free_food` / `child` 全是这个格式。

**解析**：取 `：` 前的前缀判断有无（`あり` / `なし` / `不可` / `可`）。后面的自由文本**有价值**——`private_room` 的详情里写了各种人数的包间数量，可以直接展示给用户。

## 字段映射

| 原型字段 | API 字段 | 处理 |
|---|---|---|
| 店名 | `name` | 直接用 |
| 位置 | `mobile_access` | 比 `access` 简短，适合卡片。`access` 留给详情页 |
| 车站 | `station_name` | 只有站名（"新宿"），不含出口 |
| 类型 | `genre.name` + `genre.code` | `sub_genre` 有时缺失，需判空 |
| 人均 | `budget.name` | ⚠️ 见下方「预算」 |
| 照片 | `photo.pc.m`（卡片）/ `photo.pc.l`（详情） | 最大 238px |
| 外链 | `urls.pc` | 含 `vos=` 追踪参数，**不得修改**（条款要求） |
| 容纳人数 | `party_capacity` | 宴会最大人数。`capacity` 是总席数，不是一回事 |
| 包间 | `private_room` | 前缀解析 |
| 禁烟 | `non_smoking` | 三态 |
| 支付 | `card` | 只有可否刷卡 |
| 优惠券 | `coupon_urls.pc` / `ktai_coupon` | 可作为卡片上的「有优惠券」标记 |
| 一句话卖点 | `catch` | 店家自己写的营销文案，可用于卡片副标题 |
| 评分 / 评论数 | — | **不存在**。见 ADR-004 |

### 预算

```json
"budget": { "code": "B002", "name": "2001～3000円", "average": "2900円" }
"budget": { "code": "B008", "name": "4001～5000円", "average": "4000円(通常平均)/4300円(宴会平均)" }
"budget": { "code": "B008", "name": "4001～5000円", "average": "4000円(宴会予算)" }
```

**`average` 是自由文本，不能直接当数字用。** 打分时从 `budget.name` 解析区间取中位数：`"2001～3000円"` → 2500。`average` 只作展示。

## `open` 字段解析规范

真实样本：

```
月～木、日、祝日: 11:30～翌0:00 （料理L.O. 23:30 ドリンクL.O. 23:30）金、土: 11:30～翌3:00 （料理L.O. 翌2:30 ドリンクL.O. 翌2:30）

月～木: 17:00～23:00 （料理L.O. 22:00 ドリンクL.O. 22:00）金、祝前日: 17:00～翌2:00 （...）土: 13:00～23:00 （...）日、祝日: 13:00～22:00 （...）

月～日、祝日、祝前日: 17:00～23:30 （料理L.O. 22:30 ドリンクL.O. 23:00）
```

**结构**：重复的「曜日グループ`:` 開始`～`終了 `（`L.O. 信息`）`」，**段与段之间没有分隔符**，靠下一个曜日 token 的出现来断句。

**解析要点**：

- 曜日 token：`月火水木金土日` + `祝日` + `祝前日`，连接符 `～`（范围）和 `、`（枚举）
- **`翌` 前缀表示次日**，`翌0:00` = 24:00，`翌3:00` = 27:00。判断「19:00 是否在营业时间内」时必须把终点按 +24h 处理
- L.O. 信息在全角括号内，**打分用的是 L.O. 不是闭店时间**——19:30 到店但 L.O. 19:00 等于白跑
- `close` 字段是定休日，同样是自由文本：`"なし"` / `"無"` / `"不定休あり"`

**祝日处理**：完整正确需要日本节假日日历。MVP 阶段建议忽略 `祝日` / `祝前日` 分支，只按周一到周日匹配；命中不了时降级为「不过滤 + UI 标注营业时间请以店家为准」。

**开工顺序**：先跑 `count=100` 抓一批真实 `open` 值存成 fixture，写解析器 + 单元测试，再接进主流程。不要边写边猜。

### 2026-09 实测结果（184 条真实样本，`npm run sample:open`）

比预想的规整得多 —— `open` 是机器生成的，格式高度一致：

- 解析器 `status` 全部 `ok`（0 partial / 0 failed），无「非曜日锚点」样本，无自由文本说明
- 每段结构就是「曜日组`:` 時段（（L.O.））」，段间无分隔符，靠下个曜日锚点断句 —— 和上面三条样本完全一致
- `翌` 最深见到 `翌5:00`（29:00，深夜居酒屋）
- 段内多时段（午市 + 晚市）常见，取包络 + 最晚 L.O.
- `close` 分布：约 5/6 是 `なし` / `無`，约 1/6 是 `不定休…`；**样本里没有一条是「毎週◯曜」式的明确每周定休**（`parseClose` 的曜日提取是兜底，实际很少触发）
- 结论：解析器 + `docs` 里手写的测试样本已覆盖真实数据，暂不需要把真实 fixture 提交进仓库（Recruit 条款，`fixtures/open-strings.json` 已 gitignore）

实现见 `supabase/functions/_shared/openHours.ts`，`evaluateOpen` 判「到店时刻能否赶上料理 L.O. − 60 分钟」。

## 已确认可用

- `id`（`J000694776` 格式）作为稳定主键，用于标记「吃过/喜欢/不喜欢」
- `lat` / `lng` 精度到小数点后 10 位，Haversine 距离计算没问题
- `urls.pc` 直达店铺页，卡片点击跳转按计划可行
- `genre.code`（`G001` 等）与文档一致，口味筛选可用
